# Gates

Automated enforcement for the Mandatory Engineering Constitution. Zero dependencies,
every module under 200 lines, pure rules separated from the one module that reads disk.

```
npm run typecheck    # tsc --noEmit -p jsconfig.json - checkJs + strict, 0 errors
npm run gates        # size, secrets, deps, boundaries - exit 2 on any finding
npm run trilateral   # typecheck, build, tests - three lines, exit 0 only if green
npm test             # node --test, which also runs the gates' own tests
check-all.mjs --release   # also exit 2 on a PENDING exception or open relaxation
```

## Shape

`scan.mjs` is the only module here that touches the filesystem. Every gate is a pure
function over `[{ path, text }]` tuples plus a parsed policy object, and returns findings —
never a count, never "mostly fine". That is why the gates can be tested on fixtures: a gate
that reads disk proves only that it is green today, not that it works.

`check-all.mjs` and `trilateral.mjs` are the disk-reading shells, and the only files here
with executable top-level statements — which is how the module-load gate recognises them as
entry points. `types.mjs` holds the two shapes every gate speaks (`FileTuple`, `Finding`);
`typecheck.mjs` runs the type checker for both shells, so the probe cannot contradict itself.

## The gates

### size.mjs — the 200-line rule

**Proves:** no handwritten source or documentation file exceeds 200 lines, unless a
complete entry in `policy/size-exceptions.json` raises the limit for that exact path.

The previous flat tolerance of 210 lines — a silent exception granted to every file at
once — is gone. An exception entry needs `path`, `limit`, `rationale` and `approvedBy`;
one missing any of them is itself a finding, so "add the path and move on" does not work.

**Scope, decided here:**

| | |
|---|---|
| In | `.mjs` `.js` `.ts` `.md` anywhere — tests, tools, docs, templates, examples |
| Out | `node_modules/`, `.git/` — not ours |
| Out | `LICENSE`, `NOTICE`, any extensionless file — upstream text, out by type rather than by exception |
| Out | anything under a `vault/state/` directory |

The `vault/state/` exclusion has two reasons: those files are append-only memory records
(`log.md` and `INDEX.md` grow by design, so a cap would mean deleting history to pass a
gate), and the examples' vault is generated by `examples/text-stats/reproduce.mjs`.

**Does not prove:** that a 200-line file is well designed. Length is a proxy for
reviewability, not a measure of it.

### secrets.mjs — secret-exposure scan

**Proves:** eight well-known credential shapes are absent from every text file: private
key blocks, cloud access key ids and secret-key assignments, code-forge tokens (classic
and fine-grained), model-provider API keys, chat-platform tokens, and a credential-ish
name assigned a quoted literal of eight characters or more.

This logic used to live inside `tests/leaks.test.mjs` and moved here so the CLI and the
hygiene test enforce ONE set of shapes; the test now imports the gate instead of keeping
a second copy that can drift. Privacy shapes stayed there: another question.

Every detector source is assembled from fragments at runtime, so the file holds no
literal match and never flags itself. A scanner that trips on its own rule book
teaches people to add exclusions. Exceptions go in `policy/secrets-allowlist.json`
and need `path`, `rule`, `rationale`, `approvedBy`; one without a rationale is
reported and **not** honoured. **The allowlist is empty:** each of its four entries
produced zero findings when measured, so all four went — `policy/secrets-review.md`.

**Does not prove — read this twice:** static analysis is not proof of security. The gate
proves these shapes are absent from the text it read. A credential with an unusual shape,
one in a file type we skip, one in a build artefact, or one already in version-control
history, all pass. Nothing here checks permissions, authentication or injection.

### deps.mjs — dependency integrity

**Proves** both halves of the zero-dependency claim:

1. **manifest** — `dependencies`, `devDependencies`, `peerDependencies` and
   `optionalDependencies` in `package.json` contain nothing that is not listed in
   `policy/allowed-dependencies.json` with a rationale and an approver (list empty).
2. **code** — every import specifier in a `.mjs`/`.js` file is relative or a `node:`
   built-in. Unprefixed built-ins (`fs`, `path`) count as bare and are rejected, so
   the project cannot drift into a style where a bare specifier looks normal.

Checking only (1) would miss a bare import that resolves through a hoisted
`node_modules` on one machine; only (2) would miss a declared dependency nobody imports
yet. Together they are the proof.

**Lockfile:** `package-lock.json` exists and is expected — two devDependencies are
installed, so the tree is pinned; a test asserts it holds exactly those two plus one
transitive package, both direct ranges exact. **It needs no exclusion from any gate and got
none:** `.json` is out of the size gate's scope by extension, and the secret scan reads it
like any other text and reports nothing. Measured, not assumed; a generated file that ever
did trip a gate would earn a narrow exclusion BY TYPE documented here, never an allowlist.

**Vulnerability scanning:** `npm audit` is now meaningful, and reported **0
vulnerabilities** for the installed tree on 2026-10-02. It is not wired into a gate: it
needs network, and the tree is three declaration-only packages that never reach a
runtime. The attack surface is still the Node runtime - the operator's responsibility.

**Does not prove:** anything about a dynamic `import()` whose argument is computed
at runtime — no static reader can see those. Said here rather than hidden.

### boundaries.mjs — import direction

**Proves** the arrows of the "Everything Is a Plugin" layout, as data rather than prose.
Each rule has an id, a reason written for whoever has to fix the finding, and either an
allow list or a deny list:

| Rule | Direction |
|---|---|
| `sdk-depends-on-nothing` | `eip/sdk/` → only `eip/sdk/` |
| `kernel-imports-sdk-only` | `eip/kernel/` → `eip/sdk/`, itself |
| `plugin-imports-sdk-and-own-dir` | `eip/plugins/<p>/` → `eip/sdk/`, its own directory, `examples/text-stats/src/`; never kernel internals, host, orchestration, or a sibling plugin |
| `orchestration-uses-kernel-public-entry` | `eip/orchestration/` → `eip/kernel/index.mjs`, `eip/sdk/`, itself |
| `host-composes-everything` | `eip/host/` → anything in `eip/` — composition is the one layer allowed to know all the parts |
| `kernel-and-sdk-are-transport-free` | `eip/sdk/` and `eip/kernel/` may not reach `eip/host/` or `node:http`/`https`/`http2`/`net`/`tls`/`dgram` |
| `cellular-mode-is-runtime-independent` | `tools/cellmode/`, `skills/`, `docs/`, `adapters/`, `templates/` may not import `eip/` |

`node:` built-ins pass every allow rule — this is a Node project and the standard library
is not a layering concern. A deny rule may still name one, which is how the transport rule
works. One import can violate two rules; both are reported, because each is a separate
claim a reader may care about.

`eip/` may be absent: no files matched means nothing to say, not a failure, because a
gate that failed on an absent directory would block the cell building it. Cellular Mode
must keep working in a repository with no runtime at all — the point of the last rule.

**Does not prove:** anything about `.md` files — the gate reads executable modules only,
so a code sample in a document showing a forbidden import is not a finding. Runtime
coupling through a string key, a global or an injected object is also invisible: that is
what the kernel's contract validation is for.

### trilateral.mjs — Trilateral Verification

Three independent gates after every significant change, three lines, counts included,
pre-existing failures documented rather than absorbed. The name and semantics are the
original rule; what changes here is only what each leg can honestly report.

- **typecheck** - REAL since R-1 was withdrawn: `tsc --noEmit -p jsconfig.json` with
  `checkJs`, `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` and
  `noImplicitOverride`, reported with the ERROR COUNT, never with "clean" alone.
  `typecheck.mjs` resolves `node_modules/typescript/bin/tsc` and runs it with THIS Node
  — no PATH lookup, no `.cmd` shim — falling back to `tsc` on PATH. With neither, the
  leg prints the `node --check` pass as `⚠️ … UNAVAILABLE (UNKNOWN)`: syntax is not types.
- **build** — no build step, so: module-load gate. Every non-test `.mjs` whose top
  level contains declarations only gets imported, proving it parses and that every
  specifier resolves. Entry points are excluded and **counted**, so the number never
  quietly shrinks.
- **tests** — `node --test`, reporting its own pass/fail/total counts.

**How "entry point" is decided** (`top-level.mjs`): a module is importable when its top
level holds only declarations — `import`, `export`, `const`/`let`/`var`, `function`,
`class`, comments, blanks. A module with an executable statement at top level (a call, an
assignment to something it did not declare, a `try` block) is an entry point, because
importing it would *run* it: the CLI would set the process exit code, and the example
reproducer would create and delete directories. The check is a heuristic with brace tracking,
not a parser, and conservative on purpose — a false "entry point" only skips a module from
the load gate, never passes a broken one, because skipped files still get the syntax check.

**Exit code:** 0 when build and tests are green and typecheck is not a failure. A
non-zero error count fails the leg and the run. `UNAVAILABLE` keeps the code at 0 but
the line stays a warning, never a pass - and in this repository it no longer appears.

### release.mjs — release readiness

**Proves:** no exception is honoured with `approvedBy` still `PENDING`, and no relaxation
sits in a status other than `APPROVED` or `WITHDRAWN`. Pending entries stay honoured day
to day but every run prints the count, and `--release` turns them into exit 2 — so
"release-ready" is a command, not an opinion. **Fails closed:** an unrecognised status is
`UNKNOWN`, and `UNKNOWN` blocks. **Does not prove** an approval was informed: a signature
is not a review.

## Automated vs human review

| Constitutional requirement | Status | Where |
|---|---|---|
| 200 lines per handwritten file | automated | `size.mjs` |
| Exceptions justified and approved | automated (shape), human (judgement) | `policy/size-exceptions.json` |
| No credential shapes in the repository | automated | `secrets.mjs` |
| Security by design | **human review** | static analysis is not proof of security |
| Zero RUNTIME dependencies, manifest and code | automated | `deps.mjs` |
| Dependency vulnerability scan | **manual** | `npm audit`: 0 advisories, 3 packages |
| Modularity and import direction | automated | `boundaries.mjs` |
| Contracts honoured at runtime | automated elsewhere | SDK validators + their tests |
| Type correctness | automated | `typecheck.mjs` · `jsconfig.json` · 0 errors |
| Build / module resolution | automated | `trilateral.mjs` |
| Tests pass; counts reported | automated | `trilateral.mjs` |
| Acceptance criteria written before code | **human review** | cell contracts in `vault/` |
| Never claim unexecuted results | **human review** | no gate can read intent |
| Lint / formatting | **not automated** | no zero-dependency formatter exists; style is reviewed |
| Epistemic labels used correctly | **human review** | the label is a claim about knowledge |
| Persistent memory and accountability | partly automated | the Cellular Mode CLI and its integrity test |
| Relaxations explicit and approved | automated (status), human (approval) | `release.mjs` · `--release` |

The remaining **human review** rows are the honest answer to "is this project
verified?": no, it is *checked*. Security, intent and judgement are not automatable,
and a gate that pretended otherwise would be worse than no gate.
